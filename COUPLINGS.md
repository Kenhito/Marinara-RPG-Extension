# Coupling Ledger

Every place MRR touches a Marinara Engine surface outside the documented, versioned public API. Class A = documented 2.4.3 API · B = REST route · C = engine internal (undocumented, could shift on any engine release). Every Class-C row needs a feature probe, a graceful fallback, and a visible degradation warning in the MRR panel status area.

**The Coupling Law (non-negotiable):** any commit that adds/removes/changes an engine touchpoint updates this file in the same commit. See `AGENTS.md` §8.5.

## Data-contract versions (seeded, plan §5.B14)

- `stateTagVersion` (the `[mrr-state:]` grammar): **stamped, round 7** — `MRR_STATE_TAG_VERSION = 1` (`extension/RPG-Extension-GM-Mode.js`, declared beside `STATE_TAG_RE`/`STATE_KV_RE`). One constant, no behavior change; not yet read/enforced by any parser or migration path — this closes the B14 leftover ("not yet stamped") but does not itself add grammar versioning logic.
- Ruleset schema version: `bundle.json` `version: 1` (existing).
- **B18 schema duplication hazard (2026-08-23, no engine coupling — internal maintenance note):** `schema/ruleset.schema.json`'s `resolution.oneOf` has no `$defs`/`definitions` section; all nine mode configs are inlined directly in that array (pre-existing, unchanged by B18 — restructuring it into $ref form was judged out of scope for a same-night, zero-regression build with 16 rulesets already validating against it). `additionalModes[].config` reuses each mode's field SET via nine new `$defs.resolutionConfig*` entries that DUPLICATE (not $ref) the corresponding `resolution.oneOf` branch's properties/required, minus the `mode` const. **Whoever next changes a resolution mode's fields in `resolution.oneOf` must update the matching `$defs.resolutionConfig*` by hand** — there is no schema mechanism enforcing the two stay in sync; see the `$comment` on `$defs.additionalModesArray` for the full rationale.
- Storage layout version: one record, one top-level key per `localStorage` key string, mirroring existing key strings exactly. Each value is a `{t, v}` envelope (round 4/5 — see row 1b): `t` an epoch-ms number, `v` a string or `null` (tombstone). There is no explicit version field on the envelope or the record — shape is duck-typed on read via `mrrNormalizeEnvelope` (valid envelope ⇒ finite numeric `t` + string-or-null `v`; anything else degrades to `{t: 0, v: null}` or, for a bare raw string, `{t: 0, v: <string>}`), which is also what lets a pre-envelope raw value (should one ever exist) or a hand-edited/corrupted record be read safely without a migration step.
